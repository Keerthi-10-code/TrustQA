# Phase 4 - retrieval before/after

Every table in this file is generated by `eval/phase4_report.py` from the result JSON files. The prose quotes those tables.
- `eval/results/retrieval_baseline.json` - recorded **before** any retrieval code changed.
- `eval/results/retrieval_grid.json` - flag combinations on system C (incl. reranker, decomposition, sensitivity).
- `eval/results/phase4_answers.json` (dense) and `eval/results/phase4_answers_hybrid.json` (hybrid) - full
  system C pipeline answers (generation + verification) per variant.
- Reproduce:
  ```
  python eval/retrieval_eval.py --systems C,B,A --out eval/results/retrieval_baseline.json
  python eval/retrieval_eval.py --grid --rerank --decompose --sensitivity --out eval/results/retrieval_grid.json
  python eval/answer_check.py --variants dense --out eval/results/phase4_answers.json
  python eval/answer_check.py --variants hybrid --resume --out eval/results/phase4_answers_hybrid.json
  python eval/phase4_report.py --answers eval/results/phase4_answers.json eval/results/phase4_answers_hybrid.json
  ```

## Setup
- **Questions:** `eval/dev_questions.jsonl` (`eval/questions.jsonl` does not exist yet - Phase 6). 38 questions,
  36 answerable: 12 direct, 10 table, 7 scanned, 7 multi-doc; 2 unanswerable (skipped by retrieval metrics).
  Includes the Phase 1-3 exit-check questions (F3 = T01, F4 = S02, F5 = T03).
- **Labels:** page level (filename + 1-indexed page). Each question has one evidence group per document it needs;
  a group lists every page that states that part of the answer. Each label was checked by regex against the
  chunk text of the B and C indexes, and every other page in the same document matching the regex was reviewed
  (added if it states the answer, left out if it only mentions the term).
- **Metrics:** Recall@K = share of a question's evidence groups with a chunk in the top K; all@K = all groups
  found (complete evidence, matters for multi-doc); MRR = 1 / rank of the first relevant chunk (depth 10).
  Macro-averaged over questions. **Recall@5 is the operative metric:** the generator sees the top 5 (`TOP_K=5`).
- **Fixed settings:** MiniLM-L6-v2, chunk 800/150, 694 chunks (C index `e37617963dd903b0`), RRF k=60, 50 candidates
  per retriever, quota 2 per document, MMR lambda 0.7, reranker `cross-encoder/ms-marco-MiniLM-L-6-v2`, decomposition
  by the configured LLM (qwen2.5:3b via Ollama, prompt `decompose-v1`, at most 3 sub-queries). Parameters were fixed
  before looking at the grid; the sensitivity rows vary them but were not used to choose.
- **Latency:** one `retrieve` call, model loaded, CPU (the venv's torch is CPU-only), 4-document corpus. Absolute
  values vary between runs on this machine (dense was 8 ms in an earlier identical run, 14 ms in the run below);
  compare within a table only. Decomposition latency is the qwen2.5:3b call.

## What the numbers say
1. **No variant changes overall Recall@5 beyond noise.** Every R@5 interval includes 0; one question moves R@5 by ~0.03.
2. **Hybrid (BM25 + RRF)** fixes both logged retrieval failures (F3: rank 10 -> 1; F4: not in the top 10 -> rank 2) and
   helps the categories with exact names and numbers: table R@1 0.500 -> 0.800 and R@5 0.900 -> 1.000; scanned R@5
   0.857 -> 1.000. It costs prose questions: direct R@5 0.833 -> 0.667 (D04, D09 drop out of the top 5). Overall R@5
   0.792 -> 0.778 (net -1 group), MRR +0.073 with a CI that includes 0. Latency: a few ms (BM25 over 694 chunks).
3. **Per-document quota hurts.** Alone: R@5 +0/-2 and MRR significantly lower (CI below 0). With hybrid: R@5 0.653
   (+3/-8). It forces unrelated documents into single-document answers, and it cannot help multi-doc questions where
   one document has no chunk near the top.
4. **MMR alone does nothing measurable** (R@5 +0/-1). hybrid+mmr is the best R@5 cell (0.806), but that is 1 group over
   hybrid and it was picked out of 11 variants, so it is not evidence.
5. **Cross-encoder reranker** is the only change with an MRR gain whose CI excludes 0 (+0.128 [+0.014, +0.241]); R@1
   0.375 -> 0.583. But R@5 is not better (+3/-4), D09 is lost from the top 10, multi-doc is not fixed, and it costs
   1.2-1.7 s per query on CPU (~100x dense). With the generator reading all 5 passages, rank-1 gains matter less than R@5.
6. **Query decomposition (qwen2.5:3b) does not help.** Alone it changes no question's R@5 (+0/-0) or all@5; with hybrid
   it equals hybrid within noise (R@5 0.764 vs 0.778, multi-doc all@5 1/7 vs 0/7), at ~2.9 s per query. Recorded
   sub-queries (`retrieval_grid.json`, `subqueries` per question, hybrid+decompose run): the model split only M02 into
   one query per paper; for M05 and M06 it wrote paraphrases that still name both papers; it returned M01, M03, M04,
   M07 unsplit; and it turned single-document questions (S02, S06, S07, D11, T06) into paraphrases. Where the split was right it worked: for M02 the Self-RAG A100 page, absent from the top 10 of every
   other variant, comes in at rank 6 (decompose) and 3 (hybrid+decompose). The method works; the 3B model's
   splitting does not.
7. **Multi-doc stays unsolved by every variant**: all@5 at most 0.143 (1/7). See failures.md F12.

### Answer level (dense vs hybrid, full system C pipeline)
All 38 questions, one run each, qwen2.5:3b at temperature 0, seed 0. The hybrid run was stopped twice for low system
memory and resumed (`--resume`); a game was running beside Ollama for its first 23 questions, which made qwen2.5:3b
5-30x slower, so the hybrid latency column is not comparable to dense.
- Answered 25 -> 25 of 36, Verified 17 -> 20, citing a labelled page 19 -> 21, reference numbers in the answer
  15/27 both, unanswerable abstained 2/2 both. 11 questions changed status, citation hit or reference match.
- Read answer by answer against the reference answers in `dev_questions.jsonl`:
  - **Hybrid better (5):** **S02 (F4)** abstained -> correct values on the right page (`β2 = 0.98`), Partially Supported
    because the chunk is OCR-uncertain (intended F1 behaviour); **D04** abstained -> "BART", correct; **D09** dense was
    *Verified but wrong* ("DPR's retriever", a RAG-paper quote for a Self-RAG question; F13) -> hybrid abstains;
    **T06** dense was Verified with a sentence that gives no score -> hybrid's model said "44.0" (reference 44.5) and
    verification withheld it; **M06** dense Verified an off-topic sentence -> hybrid answers from the Self-RAG pages
    (RAG retrieves regardless, Self-RAG selects), Verified, about half the reference.
  - **Hybrid worse (2):** **D10** dense gave the agreement figures (Partially Supported) -> hybrid a vague Verified
    sentence with no figure; **M07** dense covered both papers (Partially Supported) -> hybrid covers only the RAG
    ablation, Verified.
  - **Same quality, different status (4):** D03 off-target in both; S04, T02 (same top-5 set, reordered: judge
    variance), M05 (both cover only the RAG half).
- **F3 is fixed at retrieval; the answer is a caught generation error:** with hybrid, T01's row (`TAS-B=0.300`) is
  rank 1, but qwen2.5:3b answered "0.593", a number that is not in the row. Verification withheld it
  (`numeric_mismatch`); the support judge's output was also truncated at 2048 tokens and the calculation step
  returned an unparsable expression - both failed safe. Captured by re-running T01 alone (`withheld_answer`).
- **Multi-doc answers stay incomplete with both retrievers:** no multi-doc answer covers both documents' parts of
  the reference (M01-M03 abstain or are withheld, M04/M05/M07 cover one paper). F12 at the answer level.

## Recommendation (from the numbers above only)
- **RETRIEVAL_HYBRID: keep, enabled for system C** (`RETRIEVAL_HYBRID=1` in `.env`; the Config default stays off).
  It is the only near-free change with gains: it fixes F3 and F4 at retrieval, lifts table and scanned retrieval
  (TrustQA's target categories), and at the answer level it is better on 5 questions and worse on 2
  (Verified 17 -> 20, labelled page cited 19 -> 21, no unanswerable question answered). Overall
  retrieval is not significantly better on 36 questions and it loses 2 direct questions, so re-measure on the
  Phase 6 set before treating it as settled. Baselines A and B force it off (`Config.is_frozen_baseline`), and the
  eval scripts set every flag explicitly; with `.env` hybrid on, A/B/C `--systems` metrics and every top-5 chunk ID
  are still identical to `retrieval_baseline.json` (re-checked).
- **RETRIEVAL_DIVERSIFY=quota: drop.** Measurably worse alone and with hybrid.
- **RETRIEVAL_DIVERSIFY=mmr: drop.** No measured gain alone; the hybrid+mmr gain is within noise.
- **RERANK: keep off.** Significant MRR gain but no Recall@5 gain, at 1.2-1.7 s/query. Revisit only if Phase 6
  shows answers depend on rank 1, or with a GPU build of torch.
- **RETRIEVAL_DECOMPOSE: keep off with qwen2.5:3b.** No measured gain, +2.9 s/query. Re-test with a stronger LLM
  (`LLM_PROVIDER=groq`, `python eval/retrieval_eval.py --grid --decompose`) on the Phase 6 multi-doc questions.

## Caveats
- 36 answerable questions; I wrote them while reading the chunk text, so wording may share terms with the
  evidence (favours BM25). The Phase 6 set, labelled independently, is the real test.
- 4 documents only: a per-document quota of 2 in a top 5 covers almost the whole corpus, which is a harsher setting
  for the quota than a 15-document collection would be.
- Answer level: one run per variant, qwen2.5:3b at temperature 0 with seed 0; "reference numbers in answer" is a string
  check and every changed answer was also read by hand. 11 changed questions out of 38 is too few for a significance
  test; the direction is consistent with the retrieval metrics.
- The abstention gate is unaffected by construction: `RetrievedChunk.score` stays the dense cosine for every variant.
